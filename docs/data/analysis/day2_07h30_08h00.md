## Most useful takeaways

- Increase authority in stages. Begin read-only, add hidden drafts and human approval, then automate only the class of responses that has passed evaluation and production review.
- Every autonomous answer should carry evidence: root issue, source, decision path, and action taken. Confidence language without a cited source or test is insufficient.
- Missing knowledge should cause an explicit handoff, not improvisation. The SSO example correctly refuses and alerts a human.
- Knowledge-base mutation is higher risk than retrieval. Require approval for a proposed policy change, record the edit, and rerun the previously blocked example against the new source.
- Separate public explanations from internal policy. The refund denial communicates the outcome without leaking the private 14-day operating rule.
- Financial actions need narrow permissions, idempotency, audit logs, and approval thresholds. The demo lets the agent cancel/refund directly; a real system should guard the amount and action class.
- Start with one support worker and split it only when scope, permissions, or concurrency create a real boundary. Designing four roles before observing the workflow is premature.
- The knowledge-gap repair loop maps well to coding: fail safely, identify missing specification, get the authoritative rule approved, update shared context, and retry the same case.

## Condensed narrative

This half hour is a customer-support demo rather than live coding, but it offers a useful reliability pattern. The agent answers only when its knowledge base supports the response, hands off uncertain SSO questions, executes a simple refund policy, and repairs a missing policy through an approval-gated knowledge update before retrying. The strongest general lesson is a staged path to autonomy with scoped permissions, citations, traces, and explicit escalation.
