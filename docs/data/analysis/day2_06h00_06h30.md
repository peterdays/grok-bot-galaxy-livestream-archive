## Most useful takeaways

- Build specialists through the manager when possible. The manager then knows each worker's purpose, expected output, and when multiple specialists should collaborate.
- Split parallel research into explicit bounded batches and have one owner aggregate the results. “Research 200 companies” becomes five workers with 40 targets each, clear ownership, and one output contract.
- Separate machine state from the human interface. A plain CSV can be an adequate ledger if the user mainly sees ranked actions, drafts, evidence, and exceptions rather than maintaining the file manually.
- Tie automations to stop conditions as well as start conditions. A CRM stage change should remove contacts from an outbound sequence once the deal advances.
- Self-assigned model confidence is not validation. The speaker uses confidence scores, but factual accuracy should be checked against cited source data and irreversible actions should remain gated.
- Train from outcome-filtered examples: select messages that received the desired response, emphasize recent examples when the product changes quickly, and preserve older samples only for stable voice characteristics.
- Repeatedly request examples and critique specific failures. This reveals template leakage and turns “be more personal” into observable constraints.
- Keep volatile business logic—such as an evolving customer profile—in one callable skill. Update that source from new outcomes so every downstream routine consumes the same current definition.

## Condensed narrative

Although this is an SDR workshop, its architecture generalizes to coding fleets. A single manager owns specialist context, broad research is split across bounded parallel workers, persistent state is kept in a simple machine-facing ledger, and humans receive ranked actions instead of raw tables. The most reusable ideas are event-driven stop conditions, evidence-based example selection, and encoding rapidly changing shared criteria in one versioned skill.
