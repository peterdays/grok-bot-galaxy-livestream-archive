## Most useful takeaways

- Debug integrations as a chain of boundaries. For production OAuth, validate DNS, callback URLs, provider configuration, Clerk state, and the running app separately rather than treating “login is broken” as one opaque failure.
- Use the codebase as the canonical memory for implementation, but maintain explicit operational sources of truth for launch state, game rules, database schema, and work ownership.
- Run a concealed end-to-end rehearsal immediately before exposing the URL. The rehearsal catches both a data regression (“unknown bot”) and a more important experience problem: combat is too fast for players to understand.
- Product fixes should address comprehension, not just correctness. A deterministic engine can be technically right while the presentation fails; an event history with click-through steps makes the result inspectable, with autoplay added as a convenience.
- Set expectations honestly when releasing an unfinished build. Calling it a play test makes feedback the purpose of the release rather than pretending it is polished.
- Establish canonical public identities at launch. Naming the official domain and account reduces confusion and impersonation risk as traffic spikes.
- A launch pulse should be periodic and decision-oriented: current users/concurrency, practice starts, authentication conversion, matches by phase, errors, and retention signals—not a permanent dashboard created before anyone knows which question matters.
- Treat API contracts as runtime boundaries. Zod validation on frontend responses catches backend field removal or shape drift instead of letting separately generated changes fail silently.
- The claim that agents made the backend “performant” is not evidence by itself. The valuable part is that public traffic, sign-ins, load behavior, logs, and funnel data immediately begin testing that claim.

## Condensed narrative

This is the first major launch block and one of the strongest sections of Day 3. The team moves authentication into production, creates a live checklist, rehearses the full game, and catches a concrete data regression. Playing also reveals that combat is incomprehensible at its current speed, leading to a step-through event-history design. They release the build as an explicitly rough play test, monitor real users and conversion on a 15-minute pulse, then discuss a concrete engineering safeguard: validating REST payloads with Zod so independently changing frontend and backend code stays compatible.
