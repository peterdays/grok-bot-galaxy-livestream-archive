## Most useful takeaways

- Use a deliberately disposable prototype worker for uncertain visual directions. Ask for several independent implementations, review recorded evidence, and merge only the promising branch.
- A failed permission check is useful: shared docs must be placed in the team's accessible space, and agents should surface access failures instead of silently inventing missing context.
- Push back on premature schemas. The advertising worker proposed advertisers, campaigns, creatives, tables, and routes for a first billboard; the team correctly recognized that as too much for the MVP.
- Feed external feedback into a triage pipeline that clusters it, links it to the canonical project board, and proposes work. Do not automatically turn every complaint into a code change.
- One canonical design document prevents separate game-design and engineering agents from acting on diverging rules.
- Repeated micromanagement is a fleet-design smell. When the same instruction is given to several workers, update their shared template/manager policy rather than continuing one-off prompts.
- Verification should accompany parallel implementation. Cursor Projects shows a coordinator with shared worker context and separate agents that run, click, or fuzz the result.
- Recorded prototype videos are excellent review artifacts: they exposed animations that were far too fast and a “3D” result that was mostly 2.5D before any merge.
- Deleting every test is a risky shortcut. For an early disposable UI prototype, defer brittle tests; retain cheap tests for authoritative game rules, security boundaries, and regressions already discovered.

## Condensed narrative

This is one of Day 2's strongest live-building blocks. The team creates parallel 3D experiments, deals with a real document-permission issue, prevents an advertising prototype from becoming overengineered, and starts formalizing shared design context. The Cursor Projects demonstration is especially valuable: a persistent coordinator runs cloud subagents with shared memory while separate workers verify and fuzz the application. The final review of recorded prototypes shows the key discipline—inspect evidence, reject weak output, and refine direction before merging.
