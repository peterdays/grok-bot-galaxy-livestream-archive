# Day 1 — 04:00:00–04:30:00 working notes

- **04:00:00–04:01:24 — Inspect agent work and enforce proof.** The orchestrator reads cloud-agent transcripts/tool calls while work is in progress. After completion it checks required evidence—screenshots, real tests, before/after performance—and automatically replies with missing work. Very high usefulness.
- **04:01:24–04:02:30 — Deployment signals and schedules.** Monitor Vercel builds, react to failures, and schedule deployments for a specified time without keeping a local agent/laptop awake.
- **04:02:30–04:03:28 — Role-scoped persistent memory.** Keep memory relevant to each specialist so current work is not polluted by unrelated context; corrections automatically flow into future prompts to coding agents.
- **04:03:28–04:06:20 — Remote-computer and coding-agent integration.** Cloud execution removes “caffeinated laptop” hacks. Human takeover handles login/verification without surrendering secrets; first-party Cursor tools expose the same capabilities programmatically. Mostly product explanation.
- **04:06:20–04:08:51 — Unattended Slack review/unblocking.** A bot monitors Slack, applies review criteria (real tests, screenshots, code scan), runs repository skills in a cloud agent, replies with approval/status, and alerts the human only when judgment is required. Very high engineering relevance.
- **04:08:56–04:09:44 — User report → reproduction → PR.** Monitor X for bug reports, verify against `main`, fix valid issues, and send a PR. Route security/specialist reviews automatically; preserve human deep-work time.
- **04:09:48–04:11:28 — Human responsibilities and “say no” rules.** Humans retain product direction, architecture, hard performance work, and taste. Explicitly define rejected feature categories/reasons because agreeable bots otherwise accept every request.
- **04:11:28–04:13:22 — Nightly code cleanup.** At ~03:00, a research agent scans the monorepo for duplication/modularity, bloated comments, and security issues; low-risk fixes can merge only with end-to-end proof. Schedule during low-activity hours to reduce conflicts. High novelty.
- **04:13:26–04:14:47 — Slack as an internal-tool UI.** Instead of building/deploying an authenticated dashboard for a tiny workflow, let employees tag a bot with an email; a routine safely performs the action. Useful reminder to avoid unnecessary internal front ends.
- **04:14:52–04:16:20 — Auto-fix CI/deployment alerts.** Red CI triggers diagnosis and a cloud-agent repair; merge policy is predeclared; page the on-call only if unresolved after about 10 minutes. Applicable to any pipeline with a machine-readable signal.
- **04:16:21–04:18:09 — Specialist engineer fleet.** Separate UI, DevEx, and infra bots despite sharing a model, because each owns context, memory, and workflow. A chief of staff routes requests while avoiding low-level implementation context.
- **04:18:09–04:20:52 — Live onboarding of a nightly-audit bot.** Install a marketplace bot; ask an existing engineer bot to teach it the team’s Notion board, definition of clean, workflow stages, and tags; bots confirm the handoff. No copy/paste onboarding needed.
- **04:20:52–04:23:17 — Run audit and reproduce a browser bug in parallel.** Start the nightly workflow manually, then ask another bot to verify that users cannot access prior bookings by navigating the live site on its VM.
- **04:23:17–04:25:39 — “Urgent” needs a deterministic playbook.** Urgency can make agents skip steps or guess. Create an operations bot that owns and updates the shared engineering playbook; engineers inherit the same rules.
- **04:25:39–04:26:44 — Live results.** Audit bot independently fans out cloud agents; reproduction bot confirms the reported route is only a stub despite navigation linking to it.
- **04:26:44–04:30:00 — P0 escalation routine.** Every five minutes inspect active agents, detect off-track behavior such as unnecessary `sleep 300`, interrupt/nudge, and restart from the observed state. Define P0 once and refine the remembered policy through use. Very high novelty/usefulness.
