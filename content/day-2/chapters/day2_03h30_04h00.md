## Most useful takeaways

- Keep animated core characters in code when state flexibility matters; reserve generated raster assets for icons, hero art, or references. A generation-plus-background-removal chain is effective for transparent ability icons.
- Rules learned from one failure often contain the entire incident instead of the general lesson. Periodically rewrite them as short, durable principles; otherwise skills become a distracting archive of obsolete examples.
- A specialist's description should state one job, voice/behavior boundaries, inputs, and verification responsibility. “Own the engineering outcome by orchestrating, supervising, and verifying” is better than a long list of current tasks.
- Comments are a useful code-review smell when they explain why a workaround exists instead of eliminating the underlying complexity. Automated cleanup should distinguish explanatory public-contract comments from workaround narratives.
- Hiding a debug panel with a client-side feature flag is not a security boundary. If the shipped code contains balance mutation or game-resolution logic, users can invoke it; sensitive controls should be excluded from public bundles and authoritative results computed server-side.
- Parallelize only independent polish tasks. Cursor multitask mode works well here because badge color, navbar spacing, card rotation, and copy changes have limited overlap.
- Use real seed data early. Fictional marketplace bots and internal “prototype” language make the landing page feel fake even when its layout is polished.
- Play testing finds incentive exploits faster than abstract balance discussion. A visible unlimited reroll button immediately destroys rarity; fixed teams or blind rerolls preserve uncertainty.
