## Most useful takeaways

- A demonstration becomes far more reusable when the human records both the clicks and the reason for the important choices. The spoken annotation—look specifically for AI-related engineering posts—captures intent that raw replay would miss.
- Specialist collaboration can resolve a useful product question: the code agent identifies what is already wired but unused, while the competitor agent estimates what users notice and what competitors treat as table stakes.
- Letting bots propose coworkers is good for discovering missing functions, not for bypassing organization design. The live result contains a useful battle-card role and demo-grounding role, but also an AI-radar role that overlaps with Serena; human pruning is still necessary.
- Force external-facing talk tracks to ground every claim in the technical source-of-truth bot, then layer competitive contrast from the research worker. This explicitly separates verified implementation from positioning.
- Use APIs/MCPs for speed, observability, and permission control; use the browser when no supported direct interface exists. Neither path removes the need to respect service rules.
- “Ask first” inside an agent product is useful, but production safety should also be enforced at credentials, network boundaries, deployment policy, CI, and change-management layers—not solely through model review.
- The game build demonstrates disciplined subtraction: for the first visual prototype, remove authentication, database, and waitlist work; hard-code enough data to test the interaction.
- Shared context is committed into the repository rather than passed through chat alone. A new worker reads the same plan, applies stable project/design skills, proposes a small stack, and hands implementation to a coding-specialized cloud agent.
- Their explicit tool boundary is useful: Grokbot handles conversation, coordination, and persistent context; Cursor handles repository-intensive implementation.
