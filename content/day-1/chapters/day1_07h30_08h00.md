## Most useful takeaways

- Pre-call research becomes much better when it mixes public research with private usage telemetry and a first-hand walkthrough. The generated brief does not need polished UI; it needs to surface the few facts, bugs, risks, and recommendations that make a short call useful.
- Close the learning loop after the meeting. Mining call transcripts for what did and did not resonate lets the next briefing omit weak talking points and reuse lessons from other teammates' calls.
- Granting a support bot billing or account-changing power is useful but high risk. This needs narrow permissions, spend/refund caps, audit logs, approval thresholds, and an easy kill switch; the presentation mentions capability more than these controls.
- A product-change digest should not trust code metadata alone. It reconciles PRs and issue trackers against the running product, records a walkthrough, notes removed behavior, and connects the changes to outcome metrics.
- Competitive monitoring is strongest when it combines product experience, changelogs, hiring, public messaging, team changes, and direct churn reasons. Automated signups and outreach still need legal, ethical, and terms-of-service boundaries.
- Fast feedback-to-code execution moves the bottleneck to product judgment. The founder must still choose which feedback expresses a real problem and which would pull the product off course.
- For communications, a draft-first workflow is a sensible trust ramp. The agent learns from the difference between its draft and the final sent version before it receives send authority.
- Preserve specialist context by routing uncategorized one-off questions to a general “miscellaneous” worker, then explicitly transfer only durable knowledge to the appropriate specialist.
- Do a deliberate task audit instead of creating bots opportunistically. Repeated work with a clear outcome, inputs, and verification method is the best automation candidate.
- Browser automation is an expensive discovery mechanism. After one successful browser run, inspect the requests and convert the repeated workflow to a direct API/script whenever authorized and stable.
- Scheduled polling is often a hidden cost multiplier. A 15-minute routine runs about 96 times per day; trigger it from an actual event/webhook whenever possible and suppress no-op reports.
- A meta-optimization bot can inspect repeated corrections, failed routines, and avoidable questions, then update other bots' instructions and schedules. Changes should still be reviewable and versioned.
